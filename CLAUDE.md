# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A prototype build of **DGT** (Digital Governance Transmigration — formerly branded "SVKE" / Sistem Visualisasi Keputusan Eksekutif, still the name in some historical commit messages and `DGT.md`'s own spec text) for Indonesia's transmigration-area (kawasan transmigrasi) leadership, plus a companion CRUD tool for its master data. There is no build system, package manager, or test suite anywhere in this repo — everything is static, dependency-free HTML/CSS/vanilla JS, one self-contained `index.html` per tool.

## Repository layout

This directory **is** the git repository (`git init`'d here, remote `origin` → `amislaha/dgt-dashboard` on GitHub) and also the GitHub Pages site root — every push to `master` redeploys https://amislaha.github.io/dgt-dashboard/ within a minute or two. It holds three independent static sites as sibling folders, each a single self-contained `index.html` (own inline `<style>`/`<script>`, own copy of the shared design tokens — there is no shared build step to keep them in sync, so a token change made in one does not propagate to the others automatically):

- **`index.html`** (repo root) — the **home/launcher page**: https://amislaha.github.io/dgt-dashboard/. Static cards linking to the two tools below. Fronted by a `#loginView`/`#launcherView` toggle that is a **cosmetic gate only** — this is a static site with no backend, so there is no real credential check (any non-empty username/password is accepted) and `dashboard/`/`data-manager/` stay directly reachable by URL no matter its state; state lives in `sessionStorage` (`dgt-auth`), cleared by the "Keluar" link. Don't let this be mistaken for real auth, and don't build real access control on top of it without adding an actual backend. The visible UI intentionally carries no "this is a demo/prototype" disclaimer text (trimmed on request) — that context lives only here in CLAUDE.md and in code comments now, so don't reintroduce user-facing disclaimer copy without checking that's actually wanted. Add a new card to `#launcherView` here if a new tool is added as another sibling folder.
- **`dashboard/`** — the DGT situation-room dashboard itself: https://amislaha.github.io/dgt-dashboard/dashboard/. `dashboard/index.html` is described in full under "Architecture of dashboard/index.html" below — it's the file to edit for anything dashboard-related, the only copy, no separate source file to keep in sync. `dashboard/assets/kawasan/` holds real per-kawasan photos (see that section). Like the launcher, the on-page "data ilustratif / prototipe" disclaimers (topbar note, per-page footnote, map captions) were deliberately removed on request — the underlying data is still fabricated/illustrative (see Data layer below), just not called out in the UI anymore.
- **`data-manager/`** — "DGT Data Manager": https://amislaha.github.io/dgt-dashboard/data-manager/. A standalone CRUD admin tool (add/edit/delete, browser-localStorage-backed under the `dgt-data-manager:` key prefix, no server) for master data modeled on `ERD DTG 2026 (1).xlsx` (WPT/SKP/SP territorial hierarchy, komoditi, program, satker, personel, IKU) — **not** the same data model as the dashboard's illustrative `kawasan` array, and not connected to the dashboard at runtime. See `data-manager/README.md` for its entity list, data-quality caveats inherited from the source spreadsheet, and how to move data out of it (export JSON / copy-as-JS).
- `DGT.md` — the original spec (in Indonesian) for the dashboard. Describes it as an 8-module "war room" control panel meant for large-format displays (LED video wall / 4K), covering: area profiles (5T indicators), land legality (HPL/SHM geospatial overlay), demographics, infrastructure & cross-ministry collaboration, program/budget monitoring, economic/investment potential, priority scoring & early warning, and executive intelligence/AI assistant. Treat this file as the source of truth for what each dashboard module is supposed to do.

## Common commands

There is nothing to install or build. To preview a tool, just open its `index.html` in a browser (the root launcher's relative links between folders only resolve over `http(s)://`, e.g. via GitHub Pages or a local static server — opening the root `index.html` directly as `file://` still works for the links themselves, since browsers follow relative `file://` paths too).

To save and publish a change:

```bash
git add -A
git commit -m "..."
git push
```

Commits should be small and describe the user-visible change (e.g. "Add schematic map view to Geospasial module"), since the main reason this repo exists is to make it easy to look back at `git log` or revert (`git revert`/`git checkout <hash> -- dashboard/index.html`) to a prior working state.

The GitHub repo is `amislaha/dgt-dashboard` (public, required for free GitHub Pages).

## Architecture of dashboard/index.html

Everything lives in one file: inline `<style>`, inline `<script>`. The only external requests are the Leaflet CDN (`<link>`/`<script>` in `<head>`) and OpenStreetMap tiles used by the real basemap — everything else, including all imagery, is self-contained. This matters if the file is ever hosted as a Claude Artifact, which has a strict CSP blocking any external CDN/tile request: the live basemap degrades gracefully there (see below), but only actually works on GitHub Pages.

**Data layer** — near the top of the `<script>`: plain JS arrays/objects (`kawasan`, `provinces`, `ewsAlerts`, `sCurve`, `komoditas`, `infraKategori`, `klCollab`, `asalDaerah`, `nationalKPI`). All values are fabricated/illustrative, not real ministry statistics — the UI no longer says so on-screen (the "Data ilustratif" topbar note and the per-page footnote repeating it were both removed on request), so this fact now lives only here and in git history. Don't treat kawasan names, coordinates, or figures as authoritative; when adding data, keep it clearly fictional and internally consistent (`lat`/`lon` are real-world approximate coordinates used by the actual basemap; `mapX`/`mapY` are unused leftovers from a removed locator inset — ignore them, don't build new features on them).

**Chart layer** — hand-rolled SVG chart builders (`barChart`, `lineChartDual`, `donut`, `gauge`), each a plain function that takes data + an `opts` object and returns an `<svg>` element via the `el()` namespaced-element helper. No charting library. `gauge()` draws its value arc as a half-circle sweep (0–180°), so its SVG arc's large-arc-flag must always be `0` — the value angle can never exceed 180°, so it's never the "major" arc; a `frac > 0.5` style ternary there is a recurring bug (it was wrong once already), not a legitimate threshold.

**Routing / state** — a single global `state` object (current tab, selected kawasan/province, filters, sort, toggles; `state.tab` defaults to `"geospasial"`) and a `MODULES` array (id, label, sub-label) drives the left sidebar — `MODULES` lists Geospasial first since it's the landing module, not in the "01/02/03…" order the individual `renderX()` functions' own comments still use (those comment numbers are stale/cosmetic, harmless — don't renumber them just to match `MODULES` order). Each module has a `renderX()` function (`renderProfil`, `renderGeospasial`, `renderDemografi`, `renderInfrastruktur`, `renderMonitoring`, `renderEkonomi`, `renderAnalitik`, `renderIntelijen`) registered in the `RENDERERS` map. `render()` clears `#main`, toggles a `.no-pad` class on it for the immersive Geospasial layout (see below), and mounts the current tab's function output. Each `renderX()` builds its markup as an HTML template string via the `h()` helper (wraps a string in a detached `<div>`), then wires up event listeners with the `qs`/`qsa` query helpers scoped to that `wrap` element — there's no reactive framework, so any state change that should update the DOM calls a local re-render function explicitly (e.g. `renderProvGrid()`, `renderDetail()`, `renderEWS()`). The left module-nav rail itself (`#rail`, distinct from anything inside Geospasial) fully collapses on desktop via a topbar button, `#railCollapseToggle` (`.rail.collapsed` → `width:0;padding:0;border-right:none;overflow:hidden`, handing that space back to `.main`) — not an icon-only mini-rail, it disappears completely, which is why the toggle button lives in the topbar rather than inside `.rail` itself (a button inside a 0-width container would vanish along with it). This is a separate mechanism from the pre-existing mobile off-canvas `.rail.open`/`#railToggle` behavior for ≤760px, which is untouched; `checkWidth()` shows exactly one of the two toggle buttons at a time (`#railToggle` narrow, `#railCollapseToggle` wide) so there's never a redundant pair in the topbar.

**Sidebar icons** — `ICON_PATHS`/`railIcon()` hold hand-drawn 24×24 line-icon SVG path data keyed by module id, rendered via `currentColor` so they pick up the active/inactive rail color from CSS. `miniIconSvg()` reuses two of those same paths for the Geospasial style-switch buttons.

**Geospasial module layout** — `state.tab` defaults to `"geospasial"`: it's the landing view. Rebuilt (on request) as an immersive full-bleed map with a dark glassmorphism HUD sidebar overlaid on top, styled after a 3D digital-twin viewer reference image the user shared — but still a real 2D Leaflet/OSM map underneath, not 3D; there's no 3D engine or 3D city data in this project. `renderGeospasial()`'s wrap is `.geo-immersive` (`height:100%`, escapes `.main`'s padding via a `.main.no-pad` class toggled in `render()` when `state.tab === "geospasial"`), containing `#sebaranBody` (`.geo-map-full`, absolutely positioned to fill it, `z-index:1` so it forms its own stacking context — otherwise Leaflet's internal panes, which go up to z-index 700, would escape above the HUD) and `.hud-sidebar` (`#geoSidebar`, top-left, dark/blurred, `z-index:20`). The left sidebar (`#geoSidebar`) has a status readout (kawasan count, active EWS-alert count — real data, not the placeholder rainfall/weather/FPS widgets the reference image had, which were dropped since DGT has no equivalent data), a "Peta Dasar" section (`.hud-radio` buttons replacing the old `.ms-btn` style-switch — same `dasar`/`grid` options as before, no fake basemap/epoch/LoD choices), "Peringatan Dini (EWS)" (`renderEwsHud()` → `#ewsHudList`, capped at `max-height:200px` with its own scroll so it can't crowd out Daftar Kawasan below it — same `ewsAlerts` data and ack-toggle behavior as Analitik's `renderEWS()`, duplicated UI reading/writing the same array so acking in either place is reflected in both; `#geoAlertCount` in the status readout above is kept in sync on ack too), and "Daftar Kawasan" (`hudSection()` builds each collapsible section; the list section is `.hud-section.grow` so it fills remaining vertical space with its own `overflow-y:auto`). EWS living in two places (here and Analitik) is a known, deliberate-for-now duplication, not an oversight — flagged to the user rather than silently removing it from Analitik, since that module's whole premise (per `DGT.md`) is "priority scoring & early warning" together. "Detail Kawasan" (populasi, indeks 5T, legalitas HPL/SHM %, risiko, one photo) is its own **separate** panel, `#geoDetailPanel` (`.hud-sidebar-right`, top-right) — split out from the left sidebar on request. It's top-anchored with a `max-height` rather than stretched full-height like the left sidebar, deliberately leaving the bottom-right corner free for the chat FAB (see below) — don't change it to `bottom: 16px` without also moving the FAB. Both sidebars collapse independently (`#geoSidebarToggle`/`#geoSidebarReveal` and `#geoDetailToggle`/`#geoDetailReveal`, each via a `.collapsed-panel` transform — left slides left, right slides right, mind the sign when editing) on top of the left sidebar's own per-section collapse. A floating chat FAB (`#geoChatFab`, bottom-right) opens `#geoChatPanel`, a mini AI-assistant widget scoped to this module — it reuses the exact same `aiAnswer(q)` keyword-matching mock as the Intelijen module's chat (factored out to a shared top-level function specifically so the two don't drift into answering differently); its own `chatLog` array/state is separate from Intelijen's, so the two conversations don't share history. `state.geoView` still toggles the same two sub-views inside `#sebaranBody`: `renderDasar()` (Leaflet + OSM, markers at each `kawasan`'s `lat`/`lon`, kept in `leafletMarkers[k.id]` so `selectKawasan()` can `.panTo()` + `.openPopup()` a marker when it's chosen from the sidebar list instead of by clicking the map) and `renderProvGrid()` (province tiles with HPL/SHM layer-width bars — since this isn't a map, it renders as a normal light-themed `.geo-grid-pad` panel filling the canvas instead of HUD-over-map). `renderDasar()` checks `typeof L === "undefined"` and, if Leaflet failed to load (e.g. blocked by CSP), falls back to `renderDasarStatic()` instead of a live map — there used to be a third "Peta Skematik" schematic-map view (`renderPeta()`) and a small "you are here" locator inset (`renderLocator()`, `.map-locator`); both were removed earlier. The module-level `activeLeafletMap` holds the live map instance so it can be `.remove()`d before creating a new one — both on view-toggle away from "dasar" and on switching sidebar tabs (in `setTab()`), since re-rendering doesn't automatically dispose of it. Leaflet's SVG renderer sets `fill` as a raw attribute rather than through CSS, so it can't resolve `var(--x)` custom properties — marker colors use the plain-hex twin `STAGE_COLOR_HEX` instead of `STAGE_COLOR`. Selecting a kawasan (map pin, sidebar list item, or province tile) funnels through `selectKawasan()`/`renderDetail()` so all three controls stay in sync. The old cross-kawasan "Review by AI" HPL–SHM gap ranking and the standalone photo gallery panel were folded into "Detail Kawasan" (one legality % + bar, one photo) rather than kept as separate panels — there wasn't room for them as full panels in the immersive layout, and the reference's own left panel is similarly single-kawasan-focused rather than aggregate. The `.hud`-scoped badge/`.sev` color overrides near the geospasial CSS exist because the normal light-panel badge tints (soft/low-opacity, meant for a white background) go muddy on the dark glass panel — don't reuse the plain `.badge`/`.sev` colors inside `.hud` without them.

**Static basemap fallback** — `BASEMAP_STATIC_SRC` is a real OpenStreetMap tile mosaic (zoom 5, Indonesia bounding box), fetched once and baked in as a base64 JPEG data URI (~90KB of text in the `<script>`), so `renderDasarStatic()` can show actual coastlines even where live tile requests are blocked (the Claude Artifact preview). `mercatorPx()`/`basemapPct()` reproduce the exact Web Mercator projection math used when the image was built (see `BASEMAP_BBOX`, matching the crop) to place each kawasan's pin at the correct `%` position over the flat image — if you ever regenerate this image at a different zoom or bounding box, `BASEMAP_BBOX` must be updated to match or every pin will be off. There's no pan/zoom on this fallback and it's explicitly captioned as a static snapshot. It carries the required "© OpenStreetMap contributors" attribution baked into the overlay — keep that visible if this image is ever replaced.

**Area imagery** — the Geospasial "Foto-foto" gallery (`renderGallery()`) shows each `kawasan`'s real photo via its `foto` field (a relative path into `assets/kawasan/`, see below). `cityIllustration(k, w, h)` — an inline SVG skyline (gradient sky + silhouetted buildings + lit windows), seeded deterministically from `k.id` via `seededRandom()` — is the fallback rendered instead whenever a `kawasan` entry has no `foto`, so the gallery still has something to show for future entries added before a real photo exists. This illustration deliberately replaced an earlier version that pulled random stock photos (`picsum.photos`): a random photo service can't be trusted to stay thematically on-brief (a snowy scene turned up for a tropical kawasan) or, more importantly, to avoid depicting real identifiable people in a fabricated government-dashboard context — that risk doesn't apply to the curated photos now in `assets/kawasan/`. There is no separate "photo card" in the Profil drawer or the map info panels; imagery lives only in the gallery panel.

**`assets/kawasan/`** — one subfolder per `kawasan` (folder name = slug of `k.nama`, see the folder's own `README.md` for the id↔folder mapping), holding that area's real photo referenced by relative path rather than baked in as base64. This is an intentional exception to the single-file/self-contained rule above: files here won't load if `index.html` is ever previewed as a Claude Artifact (CSP blocks the relative fetch), only on GitHub Pages or opened directly as `file://`. When adding a new `kawasan`, add a same-slug subfolder with its photo and set that entry's `foto` field — until then it'll fall back to `cityIllustration()`.

**Theming** — deliberately single-theme (light "green/mint" palette defined as CSS custom properties in `:root`), not adapted for dark mode. This was originally a dark "command-center" palette (per the source spec's LED-video-wall / war-room framing) but was switched to light; don't add a dark theme without checking that's actually wanted. As of the "DGT Transmigrasi 2026" Figma design-system sync, the `:root` values (and Plus Jakarta Sans / JetBrains Mono, loaded from Google Fonts — the same CDN-dependency exception as Leaflet) are meant to track that Figma file's Colour/Type/Surfaces pages; re-pull from there rather than re-deriving values ad hoc. `--primary` is the one accent color threaded through most interactive states (was named `--gold` before the sync, when it held an unrelated green — the name is accurate now, so keep it in sync rather than reintroducing a mismatch). `--series-2` doubles as the "info" semantic and chart-series-2 color. The Geospasial module's `.hud`/`.hud-sidebar` (see below) is a deliberate, scoped exception to "single light theme" — a dark glass HUD over the full-bleed map — not a general dark-mode rollout; it uses its own hardcoded dark colors (not `:root` tokens) rather than a real dark-mode variant of the palette. Don't extend that dark styling to other modules without checking that's wanted, and don't read its existence as license to add a real dark-mode toggle.

**AI Assistant** — a keyword-matching mock, `aiAnswer(q)` (a shared top-level function, not real LLM call), only answers a fixed set of intents (mandiri, risiko, anggaran, indeks/5T) by reading the same in-page data arrays. Two separate chat UIs call it: the Intelijen module's panel (`renderIntelijen`) and the floating chat widget on the Geospasial HUD (`#geoChatFab`/`#geoChatPanel`) — each keeps its own `chatLog` array/DOM, so the two conversations don't share history, but both get identical answers to the same question since they call the same function. If the mock's intents ever grow, update `aiAnswer` once rather than each caller.
